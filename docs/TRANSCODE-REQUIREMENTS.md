# MediaIndex 按需转码与 SunnyTV 清晰度选择：开发需求

文档日期：2026-09-29
状态：2026-09-30已获用户跨仓授权，正在本地实现；尚未发布或完成NAS/电视验收。
归属：本文档保留初始需求。当前实现与限制见 [转码本地开发记录](TRANSCODE-IMPLEMENTATION.md)，后续新增约定以该记录为准。
相关记录：[8K AV1 电视起播排查](PLAYBACK-8K-AV1-2026-09-29.md)

最新产品约定：独立转码容器，MediaIndex主镜像不添加FFmpeg；选项为「原画、4K / 2160P、2K / 1440P、1K / 1080P、0.75K / 720P」。保持宽高比，不放大低分辨率源。显示文字与稳定API标识分开，其他播放器可以使用标准HLS元数据，但其已有清晰度菜单不能视为已兼容本接口。

2026-09-30续开发：当前客户端申请完整HLS VOD，采用源绝对时间轴和按需批次，替代本文初始的“起始偏移流”设计；旧live接口兼容保留。最新生命周期、拖动、暂停与验证以开发记录为准。

## 1. 问题

部分 B 站来源的高规格视频在电视上长时间停在 loading，同一 Emby 条目在手机第三方播放器可以秒播。已排查的目标样本是「周深北京鸟巢『深深的』演唱会中秋场 260925」，参数如下：

| 项目 | 实测值 |
| --- | --- |
| 文件大小 | 35,955,221,635 字节（约 35.96 GB） |
| 视频 | AV1 Main，7680×4320，8-bit，30000/1001 fps |
| 音频 | FLAC 48 kHz 双声道 |
| 总码率 | 约 24.58 Mbps |
| 时长 | 11,701.79 秒（约 3 小时 15 分） |

同一时间窗内的服务端检查结果：

- MediaIndex `0.7.34` 的 `/api/play/{token}` 在公网与本机都在 0.35 秒左右返回 302，指向 115 CDN。
- 跳转后的首部与尾部 1 MiB 都返回正确的 HTTP 206 / Content-Range。
- 从 NAS 到源站拉取 32 MiB 耗时 1.29 秒，约 26 MB/s。该数字是 NAS 到源的短时吞吐，不代表电视端网络。
- 该视频在 2026-09-28 22:03:46 触发过一次 PlaybackInfo，服务端 12.4 秒后返回 200，随后没有该条目的播放开始回报。

电视端信息：雷鸟 85 英寸鹏系列，芯片 MT9653，GPU Mali-G52 MC1。MT9653（Pentonic 700）的官方规格列出 AV1 硬件解码，同时把显示与 MEMC 上限写作 4K，未提及 8K 解码输出。这与“手机能播、电视不能播”一致：手机侧可能由软件或更强的解码器承担了 8K AV1，电视的硬解上限停在 4K。

电视端尚未取得 MediaCodec 能力表和解码器报错。目前的判断是**最可疑于电视端对该 8K AV1 码流的解码能力或驱动兼容**，不是冷门文件导致 MediaIndex 取不到原文件。这个判断需要一次转码对照播放来收口。

## 2. 已确定的产品决策

1. 继续使用 Emby 作为媒体库、元数据、海报、搜索和观看进度的唯一入口。
2. 不要求购买 Emby Premiere。免费 Emby 只提供 CPU 软件转码，硬件加速属于 Premiere；本方案绕开这条路径，不依赖 Emby 转码。
3. MediaIndex 新增可选的按需硬件转码服务，运行在用户 NAS 上，使用已有 GPU 媒体引擎。
4. SunnyTV 播放器增加清晰度选择。默认档为**原片**，保持现有链路；用户手动选择分辨率后，切换到 MediaIndex 转码流。
5. 现有 STRM、签名契约、原片 302 行为保持不变，转码是新增侧路，不是替换。

第 3 条同时解决了一个工程细节：转码不经过 Emby，就不必处理 Emby 侧 302 插件把请求重新指向原片的问题。

## 3. 目标

- 让 4K 级电视在不更换硬件的前提下，可以播放当前无法起播的高规格源，代价是分辨率与编码的降级。
- 原片路径零回归：未选择转码时，播放行为、耗时、会话回报与现在完全一致。
- 转码在用户可见的等待时间内起播，并能拖动、续播、退出释放。
- 115 取流与凭据始终留在服务器，电视端不接触网盘凭据，日志不出现签名 URL。

## 4. 非目标

- 不做下载器、转存、网盘整理，不生成整片转码文件。
- 不修改 STRM 生成规则、签名算法、Provider 凭据或 NAS 媒体文件。
- 不引入 WebView，不替换 Kotlin/Compose TV/Media3 架构。
- 不在首版做多用户并发转码集群、AI 超分、HDR 动态映射或杜比视界处理。
- 不承诺所有 8K/AV1 素材都能转码，只承诺在硬件与驱动可用的样本上验证通过。

## 5. 职责划分

| 组件 | 职责 |
| --- | --- |
| Emby 服务器 | 媒体库、元数据、图片、播放会话与观看进度 |
| MediaIndex | 115 取流解析、原片 302、按需转码会话、HLS 输出 |
| SunnyTV | 设备能力判断、清晰度选择界面、播放与切换、向 Emby 回报进度 |
| 电视 | 解码并渲染，向 SunnyTV 暴露实际解码能力 |

数据流：

```text
原片（默认）
  SunnyTV ──PlaybackInfo──> Emby
  SunnyTV ──302──────────> MediaIndex ──302──> 115 CDN

转码（用户选择分辨率）
  SunnyTV ──建会话───────> MediaIndex ──拉取──> 115 CDN
  SunnyTV <──HLS 分片───── MediaIndex（GPU 解码 / 缩放 / 编码）
  SunnyTV ──进度回报─────> Emby
```

## 6. 质量档位

| 档位 | 视频 | 分辨率上限 | 目标视频码率 | 音频 |
| --- | --- | --- | --- | --- |
| 原片 | 不转码 | 保持源 | 保持源 | 保持源 |
| 4K | H.264 High | 3840×2160 | 15–20 Mbps | AAC-LC 立体声 |
| 1080p | H.264 High | 1920×1080 | 8 Mbps | AAC-LC 立体声 |
| 720p | H.264 High | 1280×720 | 4 Mbps | AAC-LC 立体声 |

说明：

- 档位是**上限**。源分辨率低于档位时不放大，直接按源分辨率输出。
- 首版固定 H.264 作为转码编码，理由是 Android TV 兼容面最广。若客户端上报支持 HEVC，可在后续版本增加 HEVC 档位以减少码率。
- 源音频为 FLAC 时不能在 MPEG-TS 中直通，必须转 AAC。多声道直通不在首版范围。
- 码率可在设置中调整，取值范围建议 2–40 Mbps。

## 7. 用户可见行为

### 7.1 播放器清晰度入口

播放器控制层新增“清晰度”入口，位置与现有音轨、字幕面板一致，使用遥控器方向键可达。面板列出可用档位并标出当前档，默认停在“原片”。

仅在以下条件同时满足时展示该入口：

1. 当前播放地址来自 MediaIndex 播放入口；
2. 该入口所在服务上报支持转码；
3. 客户端版本满足服务端要求的最低版本。

条件不满足时，入口隐藏或只显示“原片”，不显示不可用的假开关。

### 7.2 切换行为

1. 记录当前位置 P。
2. 向 MediaIndex 请求新会话，携带目标档位与起始位置 P。
3. 新会话就绪后创建新播放器实例，播放转码流，并把进度恢复到 P。
4. 释放旧会话，避免同一内容占用两路转码。
5. 切换在界面上有明确状态（“正在切换到 1080p…”），失败时回到原档并给出原因。

切换到转码档后，本次播放不再回落到原片 302。再次选择“原片”时反向切换，回到 302 直连。

### 7.3 进度与回报

- 转码流的时间轴从**请求的起始位置**开始，因此播放器与 Emby 回报必须使用绝对媒体位置，即“流内位置 + 会话起始偏移”。
- Emby 会话回报继续使用已有 `SessionEvents` 串行机制，字段语义保持不变。
- 切换到转码档后，`PlayMethod` 需要从 `DirectPlay` 改为与转码相符的取值。此处行为需要一次真实 Emby 验证，见第 13 节。
- 拖动、暂停、退出、播放结束的续播位置以绝对位置写入，保证下次从“原片”或“转码”进入都能续接。

### 7.4 错误与降级

| 情况 | 期望行为 |
| --- | --- |
| 服务端未部署转码模块 | 不展示转码档位 |
| 硬件转码不可用 | 提示原因，保留原片继续播放 |
| 转码并发已满 | 提示“服务器正在转码其他内容”，可重试 |
| 会话过期 | 自动重建一次会话，从当前位置继续 |
| 转码中途失败 | 停止转码、保留已播进度，提示切换回原片 |
| 网络中断 | 沿用现有首帧重试策略，不叠加无限重试 |

## 8. MediaIndex 服务端需求

编号用于任务跟踪，括号内为优先级。

### MI-T01 转码能力与探测（P0）

- 启动时探测可用硬件加速后端（VAAPI / QuickSync）与实际编码器（H.264 优先，HEVC 可选）。
- 探测失败时模块处于“未启用”状态，播放入口完全不提供转码档位，不影响原片功能。
- 探测结果可通过接口查询，供客户端决定是否展示入口。
- 参考资料与本次实验环境：Emby 容器内的 FFmpeg 需要显式指定 `LIBVA_DRIVERS_PATH` 与 `LIBVA_DRIVER_NAME` 才能初始化 VAAPI；该结论只作为实现线索，实际路径以 MediaIndex 部署镜像为准。

### MI-T02 转码会话管理（P0）

- 会话与既有 play token 绑定，token 只用于定位资产，不在转码响应中回显。
- 每个会话独立 token，具备有效期与闲置超时。
- 默认单路并发，可通过配置提高；拒绝时返回明确的状态码与错误码。
- 客户端可主动停止会话；服务端在超时、异常退出、进程重启后能回收残留会话与临时文件。
- 资源上限：并发数、单会话临时空间、总临时空间、最大会话时长均可配置。

### MI-T03 转码流水线（P0）

- 输入为 115 取流地址，沿用现有解析、凭据范围、TLS 与跳转限制，不新增绕过路径。
- 视频：硬件解码 → 缩放 → 硬件编码 H.264，按档位设置分辨率上限与码率。
- 音频：转 AAC-LC 立体声。
- 字幕：首版不烧录字幕，保留外挂字幕由客户端加载。
- 分片：固定时长网格（建议 4–6 秒），分片边界与关键帧对齐，时间戳与清单保持一致。GOP 与强制关键帧参数必须显式指定，不能依赖编码器默认值。
- 起始定位：支持从指定媒体位置开始，使用输入侧快速定位后再对齐到分片网格。
- 输出：HLS 播放清单加分片，直接流式输出，不落整片文件。

### MI-T04 播放清单与拖动（P0）

首版需求目标是让播放器的进度条与拖动行为保持原生体验，即清单声明完整时长，任意位置可定位。

推荐实现：清单包含完整时长的分片序列，分片按需生成。播放器请求尚未生成的分片时，服务端保持该请求直到对应分片就绪。

备选实现：滑动窗口清单加偏移映射。此时播放器只能回看保留窗口内的内容，窗口外拖动触发会话重启。选择备选方案必须在实现前说明取舍。

无论采用哪种实现，以下条件必须成立：

- 播放器展示的总时长与源时长一致；
- 拖动后从目标位置附近起播，且起播等待时间在验收指标内；
- 分片时间戳单调递增，无重复与跳变；
- 播放结束后不重复请求已释放的分片。

### MI-T05 稳定性与资源控制（P0）

- 转码进程与 HTTP 服务解耦，进程异常不能拖垮原片 302 链路。
- 视频与音频时间戳漂移、编码器卡住、源站限速时能检测并恢复一次。
- 会话结束后释放解码器实例，避免电视长时间待机后再次播放失败。
- 临时文件写入独立目录，不写入媒体库目录。

## 9. SunnyTV 客户端需求

编号同样用于任务跟踪。

### STV-T01 来源适配（P0）

- 新增 MediaIndex 转码来源适配，集中处理能力查询、会话建立、地址拼装。按模块边界要求，UI 不拼装接口地址，播放器不直接访问网盘凭据。
- 转码服务地址从原片播放地址推导，避免新增一套服务器配置；若同一 NAS 存在多个访问入口，允许在设置中显式指定。
- 复用现有播放 HTTP 客户端策略：同一 UA、有界跳转、严格 TLS、可取消请求。
- 转码会话地址与 token 不写入日志。

### STV-T02 清晰度面板（P0）

- 在播放器控制层实现，复用现有面板的焦点隔离与返回键行为。
- 选项来自服务端能力查询结果，与本地默认值合并；本地默认值仅决定首选项，不虚构不存在的档位。
- 面板交互需要 TV 遥控器实测：进入、上下移动、确定、返回关闭、关闭后焦点回到原控件。

### STV-T03 播放切换（P0）

- 切换过程不退出播放页，不丢失当前位置。
- 切换时释放旧播放器与会话，创建新播放器，避免同时占用两路解码。
- 切换到转码档时禁用原片兜底路径，防止 Emby 侧把请求指回原片导致再次卡住。
- 绝对位置换算集中实现并覆盖单元测试，避免播放器与回报各算一套。

### STV-T04 进度回报（P0）

- 复用现有 `SessionEvents` 串行队列与最多三个事件槽的实现，不改变“保留开始与停止”的既有约定。
- 转码播放的 `PlayMethod` 取值与源信息通过一次真实 Emby 会话验证后固定下来。
- 切换档位时不产生重复的开始事件，也不丢失停止事件。

### STV-T05 设置与诊断（P1）

- 设置页提供：转码开关、默认清晰度、单次会话码率上限、服务器地址覆盖。
- 播放诊断记录保留现有字段，并增加：当前档位、会话是否复用、首次分片等待时间、转码失败错误码。诊断中不得包含完整签名地址。

### STV-T06 自动档（P2，可选）

依据设备解码能力与源参数，在设备明确不支持时提示可切换的档位。是否实现自动选择在首版验收后决定。

## 10. 接口契约草案

以下为待评审草案。实现前需要与 MediaIndex 现有路由、鉴权和版本策略对齐，草案本身不构成对 MediaIndex 的修改授权。

### 10.1 能力查询

```text
GET /api/transcode/capabilities
```

响应要点：是否启用、可用编码器、支持的档位与码率范围、最大并发、服务端版本、客户端最低版本要求。该接口不需要凭据，不得返回任何与资产或账号相关的信息。

### 10.2 建立会话

```text
POST /api/transcode/sessions
{
  "token": "<原片 play token>",
  "profile": "2160p | 1080p | 720p",
  "startPositionMs": 0,
  "videoBitrate": 15000000,
  "client": { "app": "SunnyTV", "version": "0.1.0-devXX", "deviceModel": "..." }
}
```

响应要点：

```text
{
  "sessionId": "...",
  "playlistUrl": "https://<host>/api/transcode/sessions/<id>/master.m3u8?st=<session token>",
  "startPositionMs": 0,
  "expiresAt": "...",
  "video": { "codec": "h264", "width": 3840, "height": 2160 },
  "audio": { "codec": "aac", "channels": 2 }
}
```

`startPositionMs` 是流内位置 0 对应的绝对媒体位置，客户端用它做进度换算。

### 10.3 会话控制

```text
POST   /api/transcode/sessions/{id}/heartbeat
DELETE /api/transcode/sessions/{id}
```

心跳用于维持会话并回收失联会话。停止接口需要幂等。

### 10.4 错误码

| 错误码 | 含义 | 客户端处理 |
| --- | --- | --- |
| `transcode_disabled` | 服务端未启用转码 | 隐藏转码档位 |
| `hardware_unavailable` | 硬件加速不可用 | 提示并保留原片 |
| `profile_unsupported` | 档位不支持 | 刷新能力列表 |
| `session_limit` | 并发已满 | 提示可重试 |
| `session_expired` | 会话过期 | 重建一次会话 |
| `source_unavailable` | 源地址失效 | 提示重新进入播放 |
| `transcode_failed` | 转码中途失败 | 提示切回原片 |

## 11. 安全与合规

- 115 取流与凭据只在服务器侧使用，电视端不新增网盘凭据。
- 沿用现有来源级凭据作用域、有界跳转、严格 TLS、统一播放 UA 与可取消请求。
- 日志、诊断与错误消息中不得出现签名 URL、token、Cookie 或直链主机之外的信息。
- 转码会话 token 与播放 token 分离，与会话生命周期一致，不写入用户可见的持久化配置。
- 临时分片只写入服务自有的临时目录，不写入媒体库或 STRM 目录，不触碰网盘文件。
- SunnyTV 侧不得把转码地址写入崩溃日志、播放诊断或分享内容。

## 12. 性能与容量

已实测的单点数据（仅作为可行性依据，不作为验收结论）：

| 项目 | 实测值 |
| --- | --- |
| 4K 转码（AV1 硬解 → H.264 硬编，目标 15 Mbps） | 150 帧耗时约 3.80 秒，约 39 fps，约 1.31x |
| 含解析与启动的总墙钟时间 | 约 5.74 秒 |
| NAS 到源短时吞吐 | 约 26 MB/s |

注意该实验只包含视频，关闭了音频与字幕，输出直接丢弃，且未验证长时间稳定性。

建议验收指标：

1. 4K 档首次出画不超过 10 秒（局域网、冷启动）。
2. 1080p 档首次出画不超过 6 秒。
3. 目标码率为 15 Mbps 时，稳定输出速度不低于实时速度的 1.15 倍。
4. 连续播放 30 分钟无不可恢复中断。
5. 转码进行时，原片 302 链路耗时不受影响。
6. 单路 4K 会话临时空间不超过配置上限（建议默认 2 GB，按保留窗口计算）。

NAS 需要同时承担源站下载与向电视发送转码流。局域网观看时，NAS 到电视的流量走内网；远程观看受家庭公网上传带宽限制，这一点需要在文档中明确，不承诺外网 4K。

## 13. 验收标准

分阶段验证，结果分别记录，不用一项通过代替另一项。

### 服务端

1. 能力接口在硬件可用与不可用两种情况下分别返回正确结果。
2. 建立会话、播放、拖动、停止、超时回收形成完整闭环。
3. 拖动到任意位置后起播时间符合指标。
4. 并发超限时返回规定错误码，原片路径不受影响。
5. 进程被强制结束后，残留会话与临时文件能被回收。
6. 日志抽样检查无签名 URL 与凭据。

### 客户端

1. 默认进入播放时为原片，行为与当前版本一致。
2. 选择档位后按预期切换，位置不丢失，旧会话被释放。
3. 遥控器操作面板与切换流程完整可用。
4. 服务端未部署或禁用转码时界面不出现假开关。
5. 单元测试覆盖绝对位置换算、能力合并、切换状态机。
6. Emby 观看进度在转码播放后正确写入。

### 电视实测

1. 目标样本（8K AV1）在 4K 档起播成功，记录首次出画时间。
2. 同一文件原片档复现当前失败现象，用于确认问题定位成立。
3. 至少两部其他高规格样本通过。
4. 连续 30 分钟播放，包含多次拖动与一次退出重进。
5. 记录电视端网络速率与解码器信息，形成结论。

- 本文档只定义需求与契约，不代表已获得 MediaIndex 的改动授权。

## 16. 风险与未决问题

1. 电视端 8K AV1 失败的确切原因尚未通过解码器日志确认，转码对照播放是收口手段。
2. MT9653 的 4K AV1 硬解在具体固件上的表现需要实测，不能只依据芯片规格。
3. 转码输出的编码选择（H.264 与 HEVC）会影响画质与带宽，需要在真机对比后固定默认值。
4. 清单与拖动方案的取舍直接影响实现复杂度，是首个需要拍板的技术点。
5. 长时间转码的稳定性、内存占用与编码器回收未验证。
6. 转码播放时 Emby 的 `PlayMethod` 与会话状态需要真实账号验证。
7. 源站链接刷新、限速与断流对长会话的影响未验证。
